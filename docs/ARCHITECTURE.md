# Architecture

## Current modules

- `app`: Android application entry point, Compose navigation, localized status screens, and read-only diagnostics taken from `android.os.Build`. The app currently declares no network, Bluetooth, camera, storage, accessibility, or boot permissions.
- `secure-protocol`: Android-independent Kotlin/JVM primitives for an enrolled-peer handshake and authenticated record channel. It is a protocol library, not yet connected to any Android transport, peer database, user-consent flow, or backup implementation.

The current structure is intentionally small. Features are not split into Android Gradle modules until there is an actual platform implementation to own.

## Protocol interfaces and flow

The protocol uses EC P-256 for ECDSA identity signatures and ephemeral ECDH. A host creates an invitation containing its identity public key, an ephemeral public key, a random 32-byte invitation nonce, a random server nonce, and a 120-second expiry. A client must compare the invitation identity with an already-approved peer identity before responding. The client signs a transcript containing the host invitation and its own identity and ephemeral keys. The host accepts only a client public key present in its trusted-key allowlist and verifies the signature. The host then signs the complete transcript so the client can authenticate the host.

Both sides derive 72 bytes with HKDF-SHA-256 from Google Tink 1.24.0: two independent 256-bit AES keys and two four-byte nonce prefixes. ECDSA, ECDH, SHA-256, and AES-GCM are accessed through Java Cryptography Architecture providers. `SecureChannel` binds direction, sequence number, and handshake transcript hash as authenticated data, and accepts only the exact next sequence number. Handshake messages have bounded field and total sizes. Pending handshake states are single-use.

The current JVM tests use software-generated keys. Production identity keys must be generated and used through Android Keystore. Ephemeral ECDH keys are currently generated by JCA in process memory. This protocol code must receive an independent security review before real user recovery data is sent.

## Planned platform boundaries

These are design boundaries, not implemented classes or promises:

- A `PeerIdentityStore` will own enrollment, public-key fingerprints, user approval, revocation, and audit entries. It must not grant access merely because a peer was previously paired.
- A `Transport` adapter will move bounded protocol frames over a user-selected BLE, Wi-Fi Direct, or local-network connection. Transport discovery is not identity authentication. A transport may be added only with platform-specific permission and lifecycle handling.
- A `BackupRepository` will create and restore user-selected content using Android document-provider APIs and a recovery credential independent of device identity. It must support authenticated encryption, integrity metadata, resumability, and informed destructive-action confirmation.
- A diagnostics adapter will expose only real values available through supported Android APIs and must distinguish unavailable information from a healthy result.

## Android target and local-network access

The app currently uses `compileSdk 36`, `targetSdk 36`, and `minSdk 26`. It does not yet open local sockets. Android documents Android 17 local-network protections as mandatory for apps targeting SDK 37 or higher; direct TCP/UDP LAN access then requires the appropriate runtime permission unless a privacy-preserving system picker is used. Before raising target SDK to 37 or implementing a socket transport, request only the required permission, explain it at the point of use, and test denial and revocation behavior. See [Android local-network permission](https://developer.android.com/privacy-and-security/local-network-permission).

Android Keystore keeps key material non-exportable to the app process, but hardware backing varies by device and algorithm. The app must inspect and report hardware security level instead of assuming StrongBox or a TEE. See [Android Keystore](https://developer.android.com/privacy-and-security/keystore).

## Design direction

The Compose foundation uses a quiet, high-contrast field palette with a deep botanical green accent. The interface prioritizes consent state, current capability, and clear limitations over rescue theatrics. Navigation is operable with visible text labels, supports system dark mode, and uses English and Swahili resources. The device screen reports only Android build properties that the app can actually read.
