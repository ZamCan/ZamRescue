# Architecture

## Current modules

- `app`: Android application entry point, Compose navigation, localized status/peer-management screens, read-only diagnostics, and Android platform adapters. The Peers screen explicitly creates a local identity, enrolls a peer key after full fingerprint confirmation, supports revocation, and starts/stops NSD discovery.
- `secure-protocol`: Android-independent Kotlin/JVM primitives for an enrolled-peer handshake and authenticated record channel. The protocol has not yet been wired to an Android TCP session or backup implementation.

The current structure is intentionally small. Features are not split into Android Gradle modules until there is an actual platform implementation to own.

## Protocol interfaces and flow

The protocol uses EC P-256 for ECDSA identity signatures and ephemeral ECDH. A host creates an invitation containing its identity public key, an ephemeral public key, a random 32-byte invitation nonce, a random server nonce, and a 120-second expiry. A client must compare the invitation identity with an already-approved peer identity before responding. The client signs a transcript containing the host invitation and its own identity and ephemeral keys. The host accepts only a client public key present in its trusted-key allowlist and verifies the signature. The host then signs the complete transcript so the client can authenticate the host.

Both sides derive 72 bytes with HKDF-SHA-256 from Google Tink 1.24.0: two independent 256-bit AES keys and two four-byte nonce prefixes. ECDSA, ECDH, SHA-256, and AES-GCM are accessed through Java Cryptography Architecture providers. `SecureChannel` binds direction, sequence number, and handshake transcript hash as authenticated data, and accepts only the exact next sequence number. Handshake messages have bounded field and total sizes. Pending handshake states are single-use.

The current JVM tests use software-generated keys. `AndroidKeystoreIdentityProvider` creates a separate Android Keystore P-256 ECDSA identity key, scoped to the app. Its private-key handle can be supplied to Java signature operations while key material remains non-exportable. The adapter queries and reports the available key security level; it does not force StrongBox or claim hardware backing when the provider reports software. Ephemeral ECDH keys remain generated by the protocol's current JCA implementation in process memory. No end-to-end Android handshake has been run.

## Android identity and discovery boundaries

`PeerEnrollmentRepository` validates that an imported X.509 public key is P-256, computes its SHA-256 fingerprint, and persists public peer material plus a user-assigned label and enrolled/revoked timestamps. A peer is saved only when the user re-enters the exact 64-hex-character fingerprint after comparing it in person on both phones. The UI requires reciprocal enrollment on both phones; discovery does not populate or change the trusted-peer list. Revoked records remain visible and are excluded from `trustedPublicKeys()`.

`AndroidNsdPeerDiscovery` owns explicit start/stop of DNS-SD discovery for `_zamrescue._tcp.`. Discovered service name, address, port, and optional protocol version are untrusted hints. NSD does not identify a peer, establish a socket, authenticate the handshake, or create consent. Its optional advertisement API accepts a live bound `ServerSocket`, uses an ephemeral non-identifying service name, and publishes only a version attribute; it is not invoked until a TCP listener exists. The UI stops discovery when the app backgrounds or the Peers screen is disposed. On Android versions where the system does not manage foreground multicast reception, a Wi-Fi multicast lock is held only while discovery is active.

The app manifest now declares normal `INTERNET` and `CHANGE_WIFI_MULTICAST_STATE` permissions for that discovery adapter. It does not declare Bluetooth, camera, storage, or accessibility permissions. The app targets SDK 36; Android 17 / target SDK 37 local-network runtime permission behavior and the newer NSD system picker are not implemented yet.

## Planned next platform boundaries

These are next steps, not current features or promises:

- Add a foreground `TcpPeerTransport` that owns a specific live listener and bounded stream framing. Wire NSD advertising to that listener, and connect only a user-selected discovered candidate.
- Add a `RescueSessionCoordinator` that loads the enrolled identities, compares exact invitations, runs the protocol handshake, enforces monotonic local expiry/timeouts, and requires per-operation foreground consent before any capability is granted.
- Decide target-37 LAN permission/system-picker behavior after testing both client and listening roles on actual Android versions.
- Add an audit event log and explicit identity loss/rotation workflow. Peer revocation is currently persisted, but key rotation and audit events are not implemented.
- Add a `BackupRepository` only after authenticated sessions work; use Android document-provider APIs and a recovery credential independent of device identity, with authenticated encryption, integrity metadata, resumability, and informed destructive-action confirmation.

## Android target and local-network access

The app uses `compileSdk 36`, `targetSdk 36`, and `minSdk 26`. It currently performs NSD discovery but opens no local TCP sockets. Android documents local-network protections for apps targeting SDK 37 or higher; direct LAN access will need appropriate permission handling or a suitable system-mediated selection flow. Before raising target SDK or adding TCP, request only what the implemented role needs, explain it at the point of use, and test denial/revocation on both peers. See [Android local-network permission](https://developer.android.com/privacy-and-security/local-network-permission).

Android Keystore keeps private key material non-exportable to the app process, but hardware backing varies by device and algorithm. The app must inspect and report the provider's actual key security level instead of assuming StrongBox or a TEE. See [Android Keystore](https://developer.android.com/privacy-and-security/keystore).

## Design direction

The Compose foundation uses a quiet, high-contrast field palette with a deep botanical green accent. The interface prioritizes consent state, current capability, and clear limitations over rescue theatrics. Navigation is operable with visible text labels, supports system dark mode, and uses English and Swahili resources. The device screen reports only Android build properties that the app can actually read.
